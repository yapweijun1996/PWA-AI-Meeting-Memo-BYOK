# REC03 backup and restore design

> Implementation status (`c06fadd`): completed chunk speech checkpoints are now exported and restored under the identity rules below (BUG-005). The other stores in this design (transcript pages, attempts, acoustic records) were not individually re-audited for this note and remain design-level. This document was written against `3c0e06b`.

Baseline is `3c0e06b`. REC03 already has a safe refusal path for missing completed results. This design keeps that path and specifies a bounded, portable checkpoint archive for follow-up implementation under QF04. Restore is a local operation that creates a new meeting copy. A restored copy can open for review even when its paid or acoustic processing must remain blocked. This document proposes behavior and acceptance tests. It records no new runtime results. See `task.md:54` and `docs/PRODUCT.md:164–168`.

## Failure scenarios and safe outcomes

| Scenario | Current source behavior or inference | Proposed outcome |
| --- | --- | --- |
| Restore under a new meeting ID on the same browser | **Source:** the reader assigns a new ID and resets the storage version. The UI asks before saving a copy. Progress looks up new-ID `chunkSpeech` keys. **Inference:** the copy cannot see the source meeting's rows even though they still exist locally. | Bind each imported row to a verified archive scope, then rebuild its storage key with the new ID. Preserve run, job and revision references. Keep the original intact and never fall back to reading it implicitly. |
| Restore in a different browser or profile | **Source:** archive and destination BYOK storage are independent. **Inference:** local-only results, recording chunks, keys and provider session state are absent. | Show whether the copy has checkpoint evidence and whether audio needs verified reattachment. Review works offline. Keys are entered in the destination settings before a separately confirmed provider action. |
| Partial results or interrupted local save | **Source:** the runner persists job and attempt before dispatch, then saves speech before page, final attempt and aggregate completion. **Inference:** any of these writes can be the last durable write, so adjacent records can disagree. | Reuse a validated original and repair missing local derivatives only when provenance is unambiguous. A completed marker with no valid result, unverifiable speech or conflicting provenance blocks paid resume with the affected chunk and a recovery action. Preserve other valid evidence. |
| Submitted or outcome-unknown attempt | **Source:** import converts aggregate in-flight jobs to outcome unknown and possibly charged. The current runner checks unresolved aggregate jobs and accepts explicitly reviewed chunk indices. **Inference:** a separate attempt row could be the strongest surviving evidence after a partial write. | Reconcile both ledgers. Preserve request and billing evidence. In-flight/submitted with no matching original becomes blocked and possibly charged, including after reload, repeated export and further restore. |
| Quota exhaustion mid-restore | **Source:** ordinary audio and its meeting are saved in one repository transaction, while avatars are saved separately and can report a partial restore. **Inference:** a series of new per-store writes would expose unusable state if interrupted. | Commit the bounded meeting, recovery guard and required rows together. On quota/abort, publish no new resumable meeting, preserve existing data, and let the user free space or choose an explicit review-only import. Optional avatars retain their separate and reported outcome. |
| Older archive in newer build | **Source:** legacy JSON and ZIP are validated as meeting data, with no independent checkpoint payload. **Inference:** absent rows cannot establish which chunks were never sent. | Accept supported legacy meeting schemas for review, preserve completed transcripts and billing history, and use the safe refusal path for incomplete chunked work. Resume in the original browser, or obtain a checkpoint archive there when available. An unverifiable legacy recording identity requires re-export from the original browser with its valid manifest. |
| New checkpoint archive in older build | **Source:** the legacy ZIP reader rejects unexpected entries. **Inference:** the mandatory new header is sufficient to reject this format on the inspected build, assuming the archive is unmodified. Compatibility with earlier releases requires fixtures. | Fail before writes and direct users to a compatible build in export instructions. Never silently downgrade an interrupted checkpoint archive. Earlier builds and package versions outside the compatibility matrix are unverified. |

Source for these behaviors is `src/storage/backup.ts:49–105`, `src/App.tsx:205–223`, `src/storage/repository.ts:89–111`, `src/jobs/chunked-runner.ts:23–40`, `src/jobs/chunked-runner.ts:90–124`, `src/jobs/chunked-runner.ts:127–235` and `src/features/MeetingWorkspace.tsx:815–841`. The existing legacy recovery message also offers deliberate retranscription in a **separate** meeting after new send consent. Explain that this sends a new paid request and cannot recover the previous result or settle billing for it.

## Proposed checkpoint ZIP

Keep the existing JSON and ZIP format for ordinary completed meeting backups. Add a distinct, explicitly selected **chunked recovery backup** ZIP. Its required `recovery.json` header declares the format version, source meeting ID, snapshot and run lineage, source revision, recording identity and identity version, chunk layout, section availability, and a declared inventory of fixed-name or numbered entries with bounded lengths and SHA-256 digests. Bind `meeting.json` through the inventory. Keep the archive version independent of the IndexedDB schema and the meeting-document schema. Import a supported package only after validating the whole inventory and cross-references. Unknown major versions or required features fail closed. Future optional extensions may be ignored only if the format explicitly defines that behavior and they carry no resume or provenance dependency. Hashes establish internal consistency. They cannot authenticate the author, prove billing, or establish that a snapshot is current.

- **Meeting and recording metadata.** Include the validated meeting record, plus a verified portable manifest projection with ordered indices, lengths, hashes, source ranges and lead-in. Keep ordinary audio and avatars on their existing archive paths as applicable. Omit long-audio bytes in this version. Label them absent and require the original recording for paid continuation or local acoustic work. Store the projection as expected identity metadata. The live audio manifest is published only through verified reattachment.
- **Chunk results and paid history.** Include bounded pages of normalized speech, transcript pages with immutable originals, and allowlisted attempt evidence. A result duplicated in a page and the chunk cache may share one payload only if the originals are equal and both references can be reconstructed losslessly. Describe coverage for every expected index, explicitly identifying omissions. Bind a resumable result to recording identity, chunk descriptor/index, source revision, run and known provider/model. Correlate attempt evidence to jobs and preserve billing, timestamps, safe request identifiers and assigned usage/cost fields. The existing `chunkAttempts` key is a run/chunk status slot, so preserve the aggregate job history and its IDs when recording a new attempt. An unbound legacy `chunkSpeech` row can be retained as review evidence where safe, with paid resume blocked unless corroborated by a matching page or independently recorded provenance. Never infer the original provider/model from current settings. The current runner's page repair fills those fields from the current selection. See `src/storage/chunk-speech-store.ts:6–19`, `src/storage/acoustic-store.ts:196–226`, `src/storage/acoustic-store.ts:347–362` and `src/jobs/chunked-runner.ts:83–109`.
- **Voice continuity.** Include a bounded, non-vector ambiguity summary for review and an optional, consented acoustic section as specified below. If an optional section is omitted, declare the reason and what local work can be rebuilt. Missing required data must produce an explicit blocked disposition, or an export/import refusal when even review data cannot be validated within bounds.
- **Exclusions.** Never serialize settings, provider keys, auth headers, cookies, access/refresh/session tokens, secret-bearing job handles or URLs, raw provider responses, logs, diagnostic dumps, model weights or caches. Serialize validated evidence through allowlists. Use application-generated status codes or sanitized messages for operational metadata. Keep non-secret request IDs only where their allowed shape and meaning are known. If an identifier doubles as a credential, omit it and retain the reconciliation block. Meeting content remains user data and can itself contain sensitive information. Import reads and writes no credentials and starts no verification or model download.
- **Compatibility.** Use the mandatory header as a fail-closed boundary for older readers. Never offer a legacy resume-capable export that drops the new guard or stronger sidecar evidence. For interrupted chunked work, expose checkpoint export and human-readable review export, or a legacy data export only when the recipient's ability to preserve all safety restrictions has been demonstrated. In the new build, legacy import can write an explicit review-only guard for an incomplete chunked archive. Ordinary completed JSON/ZIP remains on the tested legacy path. Archive downgrade is distinct from opening a changed local database or meeting record from an old tab. Test and block the latter before it can invoke the old runner on a protected copy.

### Bounded validation and restore

The baseline enforces a 120 MiB ZIP file and expanded aggregate limit, 64 MiB meeting JSON, 12 MiB avatar JSON, and a 24 MiB stored long-audio chunk cap. Those are source constants. Practical devices' memory, archive size, run duration, chunk/page cardinality, storage and staging headroom, codec behavior and provider limits are unverified. See `src/storage/backup.ts:6`, `src/storage/backup.ts:34–64`, `src/domain/model.ts:244` and `src/storage/long-audio-store.ts:153–167`.

Keep the existing format ceilings as upper bounds for the new format, with independently configurable ceilings for entry count, individual pages, decoded bytes and rows, meeting record growth, nesting and working set. Select and record values after synthetic memory and quota tests on the target devices. Until measured, enable checkpoint export only within a validated envelope. Prefer stored ZIP entries for the new format and bounded per-entry reads. Validate directory metadata and actual bytes, reject duplicate or unexpected paths, expansion over budget, malformed shapes, duplicate logical keys, bad hashes and dangling or out-of-scope references. Limit row count before constructing key maps. Stop with actionable recovery when an export would exceed the envelope. Keep the audio in its original file. A smaller review-only copy requires explicit user choice and must show the resulting block.

Export under the same meeting operation lock or an equivalent snapshot protocol. Read a consistent source version and scoped rows, then recheck version and write activity before publishing the package. Pause or wait for active processing, or conservatively record interrupted attempts for billing review. If no reliable snapshot protocol is available, produce a blocked recovery snapshot or refuse the checkpoint export. The current runner uses a meeting Web Lock where available. See `src/jobs/chunked-runner.ts:308–314`.

Validate and precompute all key remaps before opening the write transaction. Allocate a fresh ID, verify it is unused inside the transaction, and write the meeting record, mandatory recovery guard, chunk speech, pages, attempts and any accepted acoustic data in the same primary database transaction. Store the guard durably with the meeting, including stable lineage, expected identity, coverage, and the block reason or resume disposition. Its absence on a restored legacy chunked copy cannot authorize dispatch. Preserve source-local IDs used by references. Remap embedded storage-derived IDs and references through typed mappings, for example the meeting-prefixed assignment ID. Preserve historical recording hash provenance alongside verified portable lineage. Do not rewrite historical pages from another recording as current evidence. See `src/jobs/acoustic-continuity.ts:343–352` and `src/storage/backup.ts:12–20`.

Keep parsing, hash computation and archive reads outside the write transaction. Enforce the transaction and memory budgets before publication. Estimate available space as a preflight hint and handle unsupported estimates and real transaction failures independently. The existing quota helper returns an explicit unknown estimate. If the transaction fails, await abort before reporting failure, retain the input file, and offer retry after increasing available storage. If optional avatars fail, identify that omission and keep the successfully restored core. Cancellation, reload and duplicate imports must never expose partially resumable state or require deleting existing meetings. See `src/storage/long-audio-store.ts:62–84` and `src/App.tsx:215–223`.

## Resume decision rules

Apply the same evaluator before offering send consent and again in the runner under a meeting-scoped lock just before each dispatch. Resolve recording and chunk identity, active source revision, bound results, aggregate jobs, separate attempt rows and snapshot completeness. If provenance is conflicting or incomplete, use the more conservative disposition. Import, preview, reopening, reattachment, local page repair, local voice work and reload make zero speech submissions. A verified matching result is reusable even with an interrupted status. Keep any unresolved charge as unresolved.

| Evidence for a restored chunk | Action |
| --- | --- |
| Matching, validated paid result with consistent scope, including a result saved before final bookkeeping | Do not resubmit. Rebuild missing cache/page or finish bookkeeping locally from that result where exact provenance is available. Keep historical billing and request IDs. |
| Completed job or attempt, or `originalSaved` marker, with no validated matching result | Do not resubmit in this meeting. Show affected indices and direct the user to the original browser or a newer checkpoint archive from it. If recoverable provider evidence is available, correlate and import or fetch the original result. Otherwise keep the block. |
| Submitted, in-flight, aborted after dispatch, timed out, outcome unknown, contradictory ledger, or unknown missing evidence | Do not send automatically. Preserve possible charges. Require provider account review. A verified result is recovered locally. If an identifiable attempt has no recoverable result, a distinct manual resend requires per-attempt billing acknowledgement and fresh send consent. A generic coverage or identity gap blocks resend in the restored meeting until resolved. |
| Definitive pre-dispatch failure, with no older unresolved or completed attempt for the same chunk | Eligible for a new send only after original audio verification and fresh explicit confirmation. A submitted failure needs billing review before any confirmed resend. A failure that could have been charged or accepted remains subject to the outcome-unknown rules. |
| Demonstrably never sent in a coherent, current checkpoint, with no older matching attempt or completion evidence | Eligible for a first send after matching reattachment, takeover review and fresh confirmation. A missing row or an empty attempt list alone cannot establish this. |
| Wrong/missing audio, stale active revision or unresolved competing run | Block paid continuation. Preserve original pages, edits and jobs for review. Use verified reattachment or explicitly resolve the source/run before considering any eligible send. |

The current adapter dispatches a direct POST, and the runner records partial local state around it. Proposed resubmission is a new attempt with a new job ID. Save its intent durably before sending, fail closed if that write fails, and disable SDK, transport, queue and service-worker retries of submitted paid work. Freeze and show destination provider/model, affected chunks, data sent, known and unknown charges and the current estimate before approval. Recheck the checkpoint after approval. Consent and billing acknowledgements are scoped to that explicit action and never carried forward as permission by the archive. Preserve prior attempts and counters. Failures stop processing. See `src/providers/api.ts:94–121`, `src/providers/api.ts:311–338`, `src/jobs/chunked-runner.ts:122–160`, `src/features/MeetingWorkspace.tsx:526–545`, `src/features/MeetingWorkspace.tsx:602–617` and `AGENTS.md:16–18`.

Provider polling or retrieving an existing response operates on an already issued request under the same confirmed provider/account. It must have verified read-only semantics, bounded polling and explicit user initiation for a restored copy. Never convert “not found,” expired handles, or polling errors into a new POST for transcription. The inspected speech adapter exposes no such recovery endpoint. Provider polling and charge reconciliation capabilities are unverified. Provide manual account review as the fallback, with no network activity during import.

A file records state at export time. Browser-local locking can prevent same-origin races, but cannot coordinate disconnected browsers or an original that sends after export. Treat restored copies as passive until the user explicitly chooses one active copy, confirms the original has stopped, and reviews activity since the snapshot. Block continuation if that history cannot be reconciled. Warn when the same snapshot/lineage is restored again locally, and ensure that two copies cannot dispatch concurrently on one origin. Cross-browser exactly-once submission is unverified and requires provider support or a coordinator with verified semantics. Retain safe refusal when the needed evidence is unavailable.

## Voice data and REC01 interface

Default to checkpoint evidence without reusable acoustic vectors. Preserve the source's unresolved, ambiguous, overlapping and conflicting statuses with source/revision references as review evidence. An explicit opt-in can include current-scope embeddings (sample times and segment IDs, vectors and model provenance), anonymous identity centroids and anchors, representative evidence references, assignments with candidate scores and calibration policy, and a compatible progress checkpoint. Keep historical/provider transcripts and human decisions independent of that section. Never synthesize a match from label text, a name, missing score evidence or coincident timing. Preserve overlap and keep unknowns unresolved. See `src/storage/acoustic-store.ts:11–105`, `src/jobs/acoustic-continuity.ts:212–240` and `docs/HANDOFF.md:125`.

Proposed disclosure before export and again before restoring the acoustic section:

> Include acoustic speaker continuity data for this meeting. The file will contain numerical voice features and anonymous voice matches, including uncertain matches. Anyone with the unencrypted file can read or copy that data. The app uses it only within the restored meeting, and it does not verify anyone's real-world identity. Leaving this option off keeps the transcript and review evidence. The original recording can be reattached to rerun local voice analysis if needed.

Bind every restored active acoustic row to the same verified recording identity, current source revision and compatible model, extraction and threshold policy. Keep opted-in rows inactive until audio identity is verified. Restore interrupted local work as paused. Keep incompatible or unchecked decisions available as historical evidence where appropriate, with no automatic application. On a recording identity change, clear/invalidate derived embeddings, identities, assignments and active checkpoints before reuse. On a source revision change, mark old decisions stale and preserve human names, edits, original evidence and undo. Keep voice data meeting-scoped and delete it when the meeting is deleted. Local recomputation needs the original audio and local analysis consent. It performs no speech submission. See `src/storage/acoustic-store.ts:233–248`, `src/storage/acoustic-store.ts:368–392`, `src/storage/repository.ts:108–122` and `src/storage/repository.ts:136–168`.

**Required interface from REC01/REC02.** Request a validated, portable content identity and ordered chunk-layout projection, verification of the original manifest, and a proven legacy-to-portable hash mapping for the same verified manifest. The identity must be independent of destination meeting ID, import timestamp and MIME alias, and must bind audio bytes and timing/layout. For reattachment, require staged, cancellable verification against the expected identity and destination meeting version. Reject mismatches without activating imported checkpoints or replacing valid prior data. Activate compatible restored state only after reattachment and its metadata update both commit. Provide verified chunk reads and an unambiguous identity-changed outcome for invalidation. The baseline has primitives for manifest hashing and chunk verification and uses a staging transaction. This design depends on the interface and its measured behavior, without assuming the parallel changes' API or any cross-device codec parity. If the same source file produces different layouts, require a verifiable reproduction of the archive's layout or block continuation. See `src/storage/long-audio-store.ts:195–241`, `src/storage/long-audio-store.ts:244–276` and `task.md:52–53`.

## Owner decisions

- Approve whether the first checkpoint ZIP may offer opt-in unencrypted voice vectors or should carry only ambiguity and review evidence until encrypted export is available.
- Choose whether original-file reattachment is sufficient for the first release or whether portable backup of long audio bytes is also required. The latter needs a separate bounded format and capacity acceptance.
- Set the supported older-build matrix, target browser/device envelope and the evidence required to raise archive limits after measurements.
- Choose whether cross-browser takeover with explicit reconciliation is sufficient or whether resumable paid work must wait for a provider-side duplicate guard or coordinator. Where reconciliation cannot be verified, the copy stays blocked.
- Decide whether provider result retrieval should enter the first implementation after support is established, or whether the original browser and manual account review are the recovery paths for that release.
