## Paid-request boundary

The [Responses transport](https://github.com/earendil-works/pi/blob/9bd70ea1d044c57d412fef6d23ba53afb976dd80/packages/ai/src/api/openai-responses.ts) configures its underlying SDK with `maxRetries: 0`; its separate [retry wrapper](https://github.com/earendil-works/pi/blob/9bd70ea1d044c57d412fef6d23ba53afb976dd80/packages/ai/src/utils/provider-retry.ts) defaults to zero. Integration must still pass zero explicitly and retain negative browser tests. Do not infer that every provider adapter has this behavior. The application separately detects repeated lookups without new evidence and enforces real request/storage boundaries. Disabling transport retries alone does not prevent an agent from looping; the owner-selected 100-attempt ceiling is a safety boundary, not a quality target.

The [official GPT-6 Luna model documentation](https://developers.openai.com/api/docs/models/gpt-6-luna) lists `none`, `low`, `medium`, `high`, `xhigh` and `max` reasoning effort. Responses tool calling and the requested effort must be selected explicitly. SDK types alone do not establish model support, and the mocked payload is not provider acceptance. Computed SDK cost estimates must not be presented as provider-reported charges.

## Implemented scope and boundaries

The ordinary memo/extraction/synthesis path remains the default. With OpenAI `gpt-6-luna` or OpenRouter `openai/gpt-6-luna` selected, the confirmation offers an unchecked **Use selective transcript review (Pi, optional)** choice. This is selective evidence gathering, not a promise to read the complete transcript or discover every fact. The selected provider API key is required; sign-in tokens and arbitrary Pi adapters are not supported. OpenRouter is pinned to the OpenAI upstream; unavailable routes fail without provider fallback. Output language and meeting revision are captured in the confirmed plan.

The model receives frozen meeting metadata and speaker labels plus two read-only tools: literal `search_transcript` and `read_transcript_range`. Plans retain revision references rather than another transcript copy. Search scans at most 1,000 passages / 200,000 source characters per call. Range cursors preserve exact Unicode text, timing and original speaker IDs. Tool results are limited to 8 KiB UTF-8. Search snippets do not count as read evidence; final citations must resolve to passages actually returned by range tools. A partially read passage counts once, so the displayed passage count is neither full-text coverage nor a quality score. Claims still require human review.

Useful analysis no longer stops at six requests or 32 cumulative lookups. The later owner direction allows at most 100 cumulative provider attempts per persisted plan; completion may occur earlier and no new attempt is sent at the ceiling. Each response may declare at most 32 tools; requests remain bounded to 256 KiB serialized input, HTTP responses and decoded records to 4 MiB, and each tool result to 8 KiB. The existing 64 MiB meeting JSON and 400-entry job ledger are real aggregate-storage constraints, not quality targets. Paginated artifacts and context selection are QF04/QF05 work; this change does not promise unlimited meetings or exhaustive review. Before each request, reserve approximately 19 MiB for the next response, both final note copies and one maximum tool burst. When the next step cannot fit, stop before sending and retain previous responses. Backing up does not itself free space; separately confirmed history cleanup can remove redundant history/undo copies. Device quota and phone memory limits remain unmeasured. The model catalog's 1,050,000 context / 128,000 output limits were checked against the official model page; legacy plans without a route retain low reasoning and 4,096 output tokens. New explicit routes default to high reasoning and 32,768 output tokens; the confirmation exposes low/medium/high and 4,096/16,384/32,768 choices before the first submission. These are manual application settings, not benchmark-promoted quality profiles. All smaller byte limits still apply. QF03/QF08 must profile reasoning and output by measured quality.

Three consecutive tool rounds with no new successful tool-result content pause the run before another POST. New evidence resets that counter; previously saved results seed deduplication on explicit continuation. This is a deterministic loop guard, not a semantic quality score or exhaustive coverage test. A nine-minute timeout applies separately to each request, not the entire sequence. Human cancellation and uncertain outcomes still stop processing.

Legacy plans with `requestLimit: 6` or `null` remain readable and retain their receipts. On explicitly confirmed continuation the plan records `requestLimit: 100`, restores deterministic local tools, and sends only the next new request if its cumulative attempt count is below 100. New plans use `100`; job/context schema capacity follows the existing aggregate ledger so historical records can still be recovered. Reload, cancellation, failures and backup/restore do not reset the count. Older app builds cannot validate these new plans/backups: update all open tabs before continuing, retain a backup, and do not roll back to an older app to open a newly saved plan. This is additive read compatibility in the current app, not backward write compatibility.

Each foreground POST is fixed to the saved route (`https://api.openai.com/v1/responses` or `https://openrouter.ai/api/v1/chat/completions`), with `store:false`, no background job, no redirects, omitted ambient credentials, explicit zero SDK retries and an application fetch-once guard. A durable `in_flight` receipt precedes sending; a sanitized decoded assistant record precedes tool execution or another paid turn. Provider token usage is recorded only when a terminal provider event actually reports it. Missing usage and actual charges remain unknown; SDK catalog price placeholders never become a bill.

Errors, disconnects, cancellation and uncertain outcomes stop the loop. Reload starts no request. Explicit continuation replays only deterministic local lookups against the frozen revision, then continues useful analysis under the freshly confirmed plan. A failed/uncertain paid attempt also requires the billing-review checkbox. Unsupported/truncated final results remain available without automatic correction requests. A new correction attempt requires another confirmation. Source edits and existing memos survive processing, and new memos retain generated originals, frozen evidence and pending review.

At the 100-attempt ceiling, an already saved final response can be recovered through an explicitly local-only action. This validates the exact persisted plan, frozen sources and cited evidence without an API key, billing consent or another provider request. Invalid final content stops locally; it cannot fall through to paid correction. Full job/run history does not block this local operation, but memo-count/storage capacity, concurrent processing, revision and source checks remain enforced. Backups deliberately omit keys, so recovery from a restored backup must work without provisioning a key.

Standard memo generation saves the received response text on its job before parsing or validating it, with the active credential redacted. This also applies to each extraction and synthesis step. Processing history offers **Export recorded response**, including for a response that failed local citation or structure checks. Meeting backups include these receipts. A date quote over 200 characters remains complete in the response export. Its editable quote is left blank so a truncated condition cannot change the meaning of a deadline.

If the receipt write fails, the page holds a sanitized copy. **Retry local save only** uses the original request's transcript and settings to apply a valid response. A recovered extraction saves its evidence and pauses for explicit continuation. A recovered standalone response or final synthesis produces reviewable notes. If the output cannot be applied, the recorded response remains available for export. If another tab deleted the meeting, export the page copy and acknowledge the download before closing the page.

If assistant history in a JSON or ZIP backup disagrees with the recorded attempt order, import displays a warning and preserves the meeting, paid responses and human edits. Replay stops before using that history or submitting a request.

If a known response cannot be saved, the page retains a key-redacted recovery receipt. Further requests, deletion, navigation and PWA activation are blocked until local recovery or explicit export acknowledgement. If the receipt arrives after navigating away, the **Unsaved review response** link returns to its meeting in the same page. **Retry local save only** never contacts a provider. It acquires the existing meeting processing lock when Web Locks are available, preserves a newer plan if later attempts exist, and treats an identical saved response as a no-op so newer accounting is retained. Without Web Locks, the existing revision-checked atomic save remains the fallback. After an interruption or unsupported decoding, local retry saves only the receipt. The version 2 recovery artifact exports logical text per content kind from the received prefix. It omits raw frames and any duplicate partial decoder record. The file cannot be imported as a meeting backup. Each kind includes its joined text in arrival order, fragment count, and whether its tail was cut mid-string. The artifact also records recognized event counts and the received byte length. Exact active credentials, including supported JSON escape spellings, are masked within each joined kind. An exact match spanning independent fragments of the same kind is masked because the artifact ignores stream identities. Fragments split across different kinds or separated by other text within the same kind do not form an exact match. A response above the 4 MiB HTTP limit is stopped and only its bounded prefix is available. These in-memory copies do not survive a browser crash: keep the page open and export before leaving. Meeting JSON backups preserve saved plans, jobs and decoded records; provider keys remain in separate settings storage.

The source-grounded interaction is consistent with the published [Google NotebookLM citation workflow](https://support.google.com/gemininotebook/answer/16179559?hl=en-MY): a cited source can be opened for human review. This project keeps its own frozen local revisions and selective-coverage disclosure; Google's documentation does not establish its internal storage implementation or imply equivalent browser limits.

## Capacity regression — 2026-11-17

A synthetic meeting over 16 MiB reproduced the Chinese pre-request refusal in Chromium before the change. Afterward, Chromium and WebKit could select Pi and complete a two-request mocked review while retaining all 500 synthetic history records, saved responses and exact source citations. A separate near-limit synthetic meeting stopped before another request, retained the earlier paid-response record and human-edited note, survived a ZIP backup/restore, and resumed only after explicit local-history cleanup without resending the saved response. Synthetic worst-case tests cover escaped records, two 100-item note copies with 100 sources each, and up to 32 tool artifacts. Chinese refusal and recovery guidance were checked against a near-limit meeting without sending a request.

Local verification passed 480 unit tests, 44 targeted Chromium/WebKit cases, lint, static build, token ratchet, artifact check and both draft-safe PWA update tests. All provider responses were mocked; actual customer data, real charges, physical phones and browser quota behavior remain unverified.

## Package, CSP and delivery evidence

The manifest/lockfile pin `@earendil-works/pi-agent-core` and `@earendil-works/pi-ai` to 1.5.2. Only the core and the selected explicit Responses or OpenAI-compatible Chat Completions transport are imported for this feature. The CSP has not been weakened. A separate strict-CSP private fixture verified core success and schema rejection in both engines, with an actual blocked `new Function` sentinel; production browser cases exercise the tool round trip under the application's CSP.

The initial `fc566e4` integration, compared with a clean `c0244e8` baseline built with the same Node 22.23.3 and installed dependencies, grew emitted JavaScript from 1,457,976 to 1,899,985 bytes, an increase of **442,009 bytes raw / 119,113 summed gzip bytes**. These are historical whole-build sums, including the unchanged speaker worker, not a transferred-network or phone-memory measurement of every later build. The SDK is evaluated lazily after confirmation, but the PWA precaches its code for offline app integrity. Third-party notices add 24,486 bytes.

Vite generates bundled dependency notices. The Pi npm tarballs omit their root MIT license text, so the verified upstream notice and the schema package's TypeBox notice are additionally preserved under `docs/third-party/` and included in `THIRD-PARTY-NOTICES.md`. Artifact checks require both copyright notices; PWA installation hashes and caches the notice with other shell assets. This does not establish or change the separate WavLM derivative-weight license.
